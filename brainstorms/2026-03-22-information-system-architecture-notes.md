# 信息系统架构 brainstorm 纪要

日期：2026-03-22
主题：把现有“一次性脚本拼接”的信息收集，重构成可配置、可扩展的系统
状态：进行中（当前是阶段性共识，不是最终设计稿）

---

## 一、当前问题判断

当前系统最大的问题不是“采集不到信息”，而是：

- 结果不稳
- 过程碎
- 很多能力像脚本硬拼接
- 缺少明确架构
- 产物容易一次性，缺少稳定中间层

其中当前优先级最高的问题是：

1. 卡片/日报质量不稳
2. 过程碎
3. 入口碎
4. 资产沉淀差

进一步收敛后，最核心的问题是：

> 现在的系统缺的不是更多采集能力，而是一个稳定的架构骨架。

---

## 二、目前已经排除的架构中心

在讨论“第一公民”时，以下几个方向已被认为不适合作为系统中心：

### 1. 不是“用户订阅配置”
原因：太空泛。

例如“我要跟踪 AI”这种输入，无法天然落成足够好的日报系统。

### 2. 不是“长期跟踪对象”
原因：太窄。

不是所有信号都值得长期跟踪，不能一开始就把系统建成长期对象数据库。

### 3. 也不优先以“run / 产物”作为中心
每日批次和产物当然重要，但它们更像运行视角，而不是最合适的架构中心。

---

## 三、当前最重要的架构判断

### 1. 系统更像一个“可配置的多路召回器”
当前最接近真实需求的定义是：

> 这不是一个单纯的日报脚本，也不是单纯的对象跟踪系统，而是一个可配置的多路召回器。

每一路代表一类实际信息工作流，例如：

- GitHub 的长期跟进
- GitHub 的新项目探索
- X/Twitter 新闻
- Product Hunt

这些“路”比用户、对象、run、产物更像系统的一等公民。

### 2. “路”首先是召回器，不是渲染器
一路的职责应该收敛为：

- 有一套召回脚本 / 召回器
- 有 quota
- 吐出统一中间产物

不应该在路层过早承载：

- 输出格式
- 卡片模板
- 成稿逻辑
- 复杂编辑逻辑

也就是说：

> 路负责尽可能高质量地召回原始/准原始信号；格式化和产物表达属于路之后的层。

---

## 四、数据层偏好

### 1. 底层更偏好“原始信号”
当前偏好明确是：

- 更倾向底层以原始信号为单位
- 不喜欢只看被聚合后的新闻
- 不希望系统一上来就把内容洗成统一摘要

这意味着系统应该尽量保留：

- 原始链接
- 原始来源
- 原始上下文
- 原始对象边界

### 2. 路层默认输出“纯原始信号列表”
当前已明确选择：

> 一路默认输出 A：纯原始信号列表，尽可能不做信息裁剪。

因此第一版路层不是“小编辑器”，而是高保真召回器。

---

## 五、关于中间层的结论

### 原始信号层和日报项层需要分开，但中间层必须很薄
已经明确：

- 不能让原始信号直接裸奔进入日报
- 也不能把中间层做成很重的聚合新闻系统

因此当前最合理的结构是：

- 原始信号层
- 很薄的日报候选/日报项层
- 各类产物层

核心原则是：

> 保留原始内容的可见性，但不能取消日报项这一层。

---

## 六、原始信号的保留策略

### 按来源分层保留
当前倾向不是“全量保留”也不是“全量粗筛”，而是：

- 核心来源：高保真保留
- 外围来源：先粗筛再进入系统

这意味着系统天然需要来源分级。

### 核心来源定义目前倾向“手工白名单”
在 A（手工白名单）和 B（主题白名单）之间，当前判断是：

- 核心来源更偏向 A
- 主题池 B 更适合作为外围发现辅助

原因：

- A 更稳
- B 更容易发现新东西，但质量更飘

因此当前的总体方案不是纯 A，也不是纯 B，而是：

> A 主 B 辅

---

## 七、多路召回的当前共识

### 1. 不是固定 A7+B3 这个数字本身
最初讨论里用过 A 7 个、B 3 个作为例子，但后面已修正为：

> 不是固定 A7+B3，而是多路召回 + 多路归并，每一路有各自可配置的固定配额。

### 2. 不要复杂补位逻辑
这一点非常明确：

- 某一路不够，就不够
- 第一版不要做复杂跨路补位
- 宁可少一点，也不要为了凑数牺牲质量

### 3. 前台弱分区，后台保留来源标签
当前偏好是：

- 前台看起来是一份统一产品
- 但后台保留每个日报项来自哪一路

也就是：

> 前台统一，后台保留路标签。

---

## 八、核心/外围路径的关系

### 1. A 主 B 辅
当前最稳定的策略是：

- 核心白名单路负责稳定主干
- 主题发现路负责引入新东西

### 2. B 路宁缺毋滥
外围发现路质量不足时：

- 不为了 quota 凑数
- 不强行塞低质量候选

---

## 九、核心对象在产物中的组织方式

已经明确选择：

> 默认按对象级输出；如果同一对象当天发生多个异质且都重要的变化，可以拆开。

也就是：

- 不默认按事件级碎片化输出
- 也不把所有不同变化硬揉成一团
- 采用“对象级为主，必要时拆分”的混合方式

---

## 十、长期跟踪对象的状态偏好

### 升级：半自动
系统可以提出：

- 建议升级为长期跟踪对象

但是否加入长期观察池，由人确认。

### 降级：半自动
系统也可以提出：

- 建议降低优先级/移出长期跟踪

但最终仍由人确认。

也就是说：

> 系统负责发现趋势和提出建议，人负责拍板长期观察面。

---

## 十一、A 路（核心池）的当前偏好

### 核心池不等于每天固定出现同样几个对象
当前已明确选择：

> 固定对象池 + 当日有更新才占槽。

含义：

- 核心池是一组长期关注对象
- 但当天没有值得写的更新，就不硬塞进日报
- 不为了“看起来稳定”而制造假稳定

---

## 十二、去重策略的阶段性选择

### 1. 跨路去重：第一版先不做
当前明确选择：

> 第一版先不做跨路去重。

理由：

- 先确认多路召回器本身成立
- 不为了聪明而把第一版做重

### 2. 路内去重：暂定极晚处理/尚未定稿
在本轮问答里，用户倾向先把结构落 markdown 再继续，因此这一块还没有最终定稿。

---

## 十三、当前形成的阶段性结构图（非最终设计）

目前最接近共识的高层结构是：

1. **路（控制面第一公民）**
   - 每一路是一个召回器
   - 每一路有自己的来源、意图、quota
   - 每一路尽量高保真地产出原始信号

2. **原始信号层（数据面第一公民）**
   - 尽量保留原始上下文
   - 不过早裁剪
   - 作为后续产物的共同底座

3. **很薄的日报候选/日报项层**
   - 不直接等于原始信号
   - 但也不做重聚合

4. **产物层**
   - 日报
   - 卡片
   - 周报
   - 推送
   - 后续其它视图

一句话概括就是：

> 以“路”为控制面中心，以“原始信号”为数据面中心，中间只保留一层很薄的日报项转换。

---

## 十四、进一步明确：路是一等公民，且更像“强声明式可配置召回器”

后续讨论进一步收敛出新的关键共识：

### 1. “路”可以作为系统第一公民
相比用户、对象、run、产物，当前更接近真实需求的是：

> 路（lane / route / channel）是一等公民。

原因：

- 用户真正配置的是“信息工作流”，不是抽象订阅
- 长期对象太窄，run / 产物更像运行视角
- 路更贴近真实业务表达，例如：
  - GitHub 长期跟进
  - GitHub 新项目探索
  - X 新闻
  - Product Hunt

### 2. 路首先是召回器，不是渲染器
一路的最小职责进一步收敛为：

- 召回脚本 / 召回器
- quota
- 统一中间产物协议

不应过早承担：

- 输出格式
- 卡片模板
- 成稿逻辑
- 重编辑逻辑

### 3. 路的输出协议：typed JSONL 原始信号流
当前新增的明确偏好是：

> 一路应输出结构化、typed 的 JSONL 原始信号流，而不是一坨 markdown 或自然语言摘要。

每条 signal 至少应有公共字段，并按 `type` 扩展不同字段。

例如：

- `github_project`
- `github_release`
- `x_news`
- `producthunt_product`

这意味着路与后续层的接口不再是文本，而是结构化信号。

### 4. schema 偏好：半强 schema
对于 typed signal 的 schema，当前偏好是：

- 公共字段统一
- 每个 `type` 有必填字段与推荐字段
- 不同路逐步补齐
- 先不要一上来做成强 schema

### 5. 公共字段最小集合（当前版本）
公共字段当前最小集更新为：

- `type`
- `lane`
- `source`
- `url`
- `fetched_at`
- `title`

说明：最初讨论过更极简公共字段，但后续补充认为 `title` 至少必须存在。

### 6. 路配置组织：总配置文件
当前偏好不是一路一个文件，而是：

> 先用一个总配置文件统一列出很多路。

原因：

- 第一版更便于总览和统一调参
- 不希望一开始就文件系统碎片化

### 7. 路配置风格：强声明式
当前明确选择：

> 尽量让“加一路”变成配置动作，而不是开发动作。

这意味着未来系统更像一个 lane runtime：

- `kind` 决定调用哪类召回器
- 配置提供参数
- runtime 负责校验、执行、输出 typed JSONL

### 8. 第一版 lane kind 数量：中等规模（4~6 个）
第一版不想只有 2~3 个 demo 路，也不想一次吞掉全部来源，而是希望：

- 先覆盖当前主要信息工作流
- 但仍保持范围可控

当前优先的 kind 候选是：

- GitHub 固定 repo 更新
- GitHub 新项目发现
- X 指定账号 / 关键词
- Product Hunt

---

## 十五、样板路：GitHub 固定 repo release 路

在“GitHub 固定 repo 更新”里，当前又进一步收敛成更窄、更稳定的第一条样板路：

> GitHub 固定 repo 的 release 路

即第一版先不处理 PR / issue / README diff / commit / discussion，只处理 release。

### 当前已明确的约束

#### 1. 原始信号类型
当前只选：

- `release`

#### 2. release signal 字段策略
当前偏好是“尽量全保留”，至少应包括：

- repo 名 / owner-repo
- release 标题
- tag / version
- 发布时间
- release 链接
- release notes 原文
- release body 的结构信息
- 可能的 assets / 附件
- compare link / source commit（如可拿到）

即：

> 第一版 release signal 不做“只取关键字段”的裁剪，而是尽量把 release 这件事完整保下来。

#### 3. quota 解释
对于这条 release 路，quota 当前偏好是：

> 按 repo 限定，而不是按整条路总数限定。

也就是：

- 对每个 repo
- 最多取最近 1 个 release

#### 4. 时间窗口
当前偏好是：

> 最近 N 天，可配置

而不是固定 24 小时或只看上次 run 以来的增量。

---

## 十六、当前去重策略的进一步收敛

### 1. 跨路去重：第一版先不做
这个结论保持不变。

### 2. 路内去重：第一版也先不做
后续进一步明确：

> 为了先把“多路高保真召回器”跑通，第一版路内去重也先不做。

因此当前总体节奏是：

1. 先把路跑通
2. 每路高保真吐原始信号
3. 先接受一定重复
4. 后续再加去重层

- signal pool 这一层是否先只做索引汇总
- 从 signal pool 到日报候选项的最小转换规则
- 未来是否、何时引入跨路去重与跨路排序
- 多种产物如何共享同一批日报项
- 哪一层负责“进入长期跟踪对象”的建议生成

## 十八、第一阶段进一步收敛：先不引入 briefs，只做到 signal pool

后续讨论又明确了一件非常关键的事：

> 当前阶段先不引入 `briefs/` 层。

也就是说，第一阶段不讨论：

- brief item
- 日报候选项
- 卡片项
- 合并规则
- 最终成稿文档

第一阶段只做：

- lane
- typed JSONL signals
- signal pool
- date-first 存储
- 统一 `index.json`

这意味着当前阶段的核心不是“日报系统完整闭环”，而是：

> 一个强声明式、文件系统优先的多路信号召回系统。

## 十九、signal pool 的角色与实现

### 1. signal pool 先做“轻索引池”
在“只是归档池”和“轻索引池”之间，当前选择是：

> signal pool 第一版应是轻索引池。

也就是：

- 不只是把 JSONL 文件堆在一起
- 还要能按 lane / type / 时间 / source 做基础索引和浏览
- 但还不是计算池，不急着做复杂派生字段

### 2. signal pool 实现方式：文件系统优先
当前明确选择：

> 先用文件系统作为 signal pool 的主实现，不优先上数据库。

原因：

- 可读
- 易 debug
- 易 diff
- 易回放
- 符合第一阶段“给人看 + 给程序接”的目标

### 3. 目录组织：按日期优先
当前偏好不是按 lane 优先，而是：

> signal pool 目录按日期优先组织。

形式类似：

- `signals/2026-03-22/github-release.jsonl`
- `signals/2026-03-22/github-discovery.jsonl`
- `signals/2026-03-22/x-news.jsonl`
- `signals/2026-03-22/producthunt.jsonl`

这说明第一阶段的主消费场景仍然是：

> 今天发生了什么、今天各路召回了什么。

### 4. 每天需要统一 index.json
当前明确选择：

> 每个日期目录里应有一个统一的 `index.json`。

该文件第一版只负责运行元信息，不负责统计报表，也不负责候选层预埋。

它至少应记录：

- 今天有哪些 lanes 跑了
- 各 lane 是否成功/失败
- 每路输出文件路径
- 每路条数
- 每路配置摘要
- 时间窗口 / quota 等运行参数

### 5. signal 和 brief 必须物理分层
虽然当前阶段不引入 `briefs/` 层，但已经明确：

> 将来 `signals/` 和 `briefs/` 必须物理分层。

原因：

- 避免原始信号与产物层混在一起
- 保证高保真原始层不被后续产物污染

## 二十、样板 lane 进一步细化

### 1. 第一条样板 lane
当前第一条样板 lane 明确为：

> GitHub 固定 repo 的 release lane

### 2. lane kind 第一版优先集合
当前第一版优先覆盖的 lane kinds 为：

1. GitHub 固定 repo 更新（已进一步收敛为 release lane）
2. GitHub 新项目发现
3. X 指定账号 / 关键词
4. Product Hunt

### 3. lane 配置风格
当前已明确：

- 一个总配置文件统一列出所有 lanes
- lane 采用强声明式配置
- 第一版先做中等数量（4~6 个）kind

也就是说未来系统更像一个 lane runtime，而不是一堆手写脚本集合。

---

## 二十一、阶段一完成标准

当前阶段一的完成标准明确为：

> 不仅要能跑，还要同时满足“人类可检查”和“程序可消费”。

### 给人看
需要做到：

- 目录清晰
- JSONL 可读
- index 清晰
- 容易 debug / 回放 / 追溯

### 给程序接
需要做到：

- schema 稳定
- 文件命名稳定
- index 可解析
- 后续层无需重新猜字段与来源

这说明第一阶段不是技术 demo，而是真正的基础设施阶段。

---

## 二十二、仓库边界

当前明确选择：

> 这套系统应放在一个独立仓库中，专门承载这套日报系统。

原因：

- 不与现有 `memory` / `github-daily` / `x-daily` 历史包袱缠绕
- 更容易把系统做成真正的产品骨架
- 后续扩展 briefs / daily / cards / weekly 时边界更清楚

---

## 二十三、当前最重要的架构句子

目前可以暂时把系统定义为：

> 一个强声明式、文件系统优先、独立仓库承载的多路信号召回系统。每一路按自己的意图从不同来源召回高保真的 typed 原始信号，并以 JSONL 结构化输出；系统先把这些信号沉淀到按日期组织的 signal pool 中，并配套统一的 index.json，第一阶段优先保证路能成立、信号足够全、结构可检查也可程序消费，而不提前引入 briefs 和最终日报产物层。
