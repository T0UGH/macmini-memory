# Claude Code 正在替代一整段软件生产流程
*从 coding 到 debugging，再到 design，我对这场变化的最新判断*

我现在对 Claude Code 的判断很直接：

- coding：100%
- debugging：75%-85%
- design：70%

如果这个判断成立，那它替代的就不是“写代码”这一个动作，而是一整段软件生产流程。

我第一次真正意识到这一点，是刚从公司内部 AI 工具切到 Claude Code 的时候。

当时我用 OpenSpec 跑出了一个需求级别的新功能。不是 demo，也不是补函数，而是一个真实需求，涉及多个微服务改动，最后出了 1000 多行代码。

这件事最重要的地方，不是“它很强”。

而是它已经能接需求级任务，不是函数级任务。

只要它能接需求级任务，它替代的就不只是 coding，而是从理解需求、拆任务、写实现，到 debugging 和 design 里大量可结构化的部分。

这里真正的变化也不只是能力变强，而是 workflow 变了。

我们现在不是把 Claude Code 当补全工具用。我们跑的是 superpowers 这套流程：

- brainstorm
- task
- apply
- review
- UT

所以变化不是“AI 帮我提效”。

而是原来很多靠人手工推进的执行工作，已经被放进了一套固定的人机协作流程里。

很多人会说，人还重要，因为 AI 还有 gap。这当然没错。

合作方隐藏约束、内部平台默认规则、未文档化习惯、历史包袱和兼容逻辑，这些确实是 AI 现在的 gap。

但这些 gap 不应该被当成人长期价值的核心。相反，它们应该被持续清除。

- 该文档化的文档化
- 该结构化的结构化
- 该沉淀进工作流的沉淀进工作流
- 该交给 AI 的继续交给 AI

所以人真正重要的，不是一直替系统背这些脏知识。

人真正重要的是三件事：

- 产品思维
- 架构设计
- 代码品味

产品思维决定你有没有定义对问题。  
架构设计决定你有没有把系统组织对。  
代码品味决定你能不能判断什么实现是真的好，什么只是暂时能跑。

所以我现在更认同的说法是：

> 以后工程师拼的不是谁写得快，而是谁想得更清楚、设计得更对、判断得更准。

很多人现在还在低估 Claude Code。我觉得原因很简单：不是他们判断差，是他们还没真正开始用。

不是没听过，也不是试过几次，而是没有把它真正接进工作流。

这里面最关键的不是 control，而是 context。

> 很多人不是高估了 AI，而是严重低估了上下文的价值。  
> 不是 control，是 context。给够上下文，再配上 SOTA 模型和 SOTA agent，它几乎什么都能做。

所以我现在看一个工程师会不会真正用 Claude Code，不是看他有没有装这个工具，而是看他有没有最小工作流。

在我看来，最少要有三样：

1. `claude.md`
2. skill
3. spec kit，比如 superpowers

没有这三样，它很容易退化成聊天工具。  
有了这三样，它才会真正进入生产流程。

所以最后我的结论也很直接：

**会不会写代码还重要，但已经不是最重要的了。**

真正越来越重要的是：

- 产品思维
- 架构设计
- 代码品味

AI 不是在简单替代工程师。  
AI 在把工程师从执行层往上推。

你如果上不去，会很难受。  
你如果上得去，价值会更集中。

我觉得这件事已经发生了。  
而且不会回去。
